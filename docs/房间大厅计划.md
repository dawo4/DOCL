# 房间大厅 · 实施计划

> 状态：**暂缓**。预计几个大版本之后再做，先留档。

目标：玩家在启动器里能看到别人开的陶瓦房间并一键加入；房主开房后房间自动出现在列表，关房后自动消失。

---

## 一、现状（已具备，不用重做）

| 能力 | 位置 |
| --- | --- |
| 拉取大厅列表 `GET hall_url`，兼容 `{"rooms":[...]}` 和裸数组 | `src-tauri/src/hall.rs` |
| 房间结构 `room / name / motd / players / max_players / version / loader / mods / updated` | `HallRoom` |
| 进房前的版本 / 加载器 / Mod 比对提示 | `commands::room_mod_check` |
| 加入房间（陶瓦邀请码） | 联机页「陶瓦房间」 |
| 大厅地址配置项 `hall_url` | 设置 → 联机 |

也就是说：**客户端读大厅的能力已经完整**，缺的是"谁来提供这份 JSON"，以及"房主怎么把自己的房间报上去"。

---

## 二、缺口

1. 大厅服务端：一个只做增删查的小 HTTP 服务。
2. 客户端上报：开房后定时上报房间，关房后停止。
3. 服务端超时下架：房主异常退出时不留下僵尸房间。
4. 基础治理：限流、字段长度、字符过滤。

---

## 三、阶段一：迷你大厅服务端（可本地跑通）

**技术选型**：Rust + axum（与客户端同语言，单 crate 即可）；存储先用内存 `HashMap`，需要持久化再加 SQLite。

**接口**

- `GET /rooms`
  返回 `{"rooms":[...]}`，字段与 `HallRoom` 保持一致，按 `updated` 倒序，最多 100 条，已超时的房间不返回。
- `POST /rooms/heartbeat`
  Body：`{"room","name","motd","players","max_players","version","loader","mods":[...]}`
  以 `room`（陶瓦邀请码）为 key 做 upsert，`updated = now`。
- `DELETE /rooms/{room}`（可选）
  房主主动关房时调用，立即下架。

**规则**

- 心跳超过 **90 秒** 未更新即视为失效，不再返回。
- 字段长度：`name ≤ 40`、`motd ≤ 120`、`mods ≤ 200` 项（超出截断）。
- 单 IP 每分钟写入次数限制，超限返回 429。
- 房间数上限 100（与客户端 `MAX_ROOMS` 对齐）。

**验收**：本地 `curl` 打一次心跳 → `GET /rooms` 能看到 → 90 秒后自动消失。

---

## 四、阶段二：启动器端上报

- 联机页「陶瓦房间」增加「公开到大厅」开关（默认关）。
- 开房成功、拿到邀请码后启动心跳任务：
  - 每 30 秒 `POST /rooms/heartbeat` 一次；
  - 关房、退出页面、启动器退出时停止，并尽量发一次 `DELETE`。
- 上报内容：邀请码、房间名、MOTD、当前人数、游戏版本、加载器、Mod 列表（用 `moddeps::installed_ids` 或 jar 文件名）。
- 上报失败静默重试，不影响联机本身。
- 设置页 `hall_url` 的默认值改为正式地址。

**验收**：两台机器，A 开房并勾选公开，B 在「房间大厅」看到该房间并能加入；A 关房后 B 刷新列表房间消失。

---

## 五、阶段三：体验与治理（按需）

- 列表筛选：版本、加载器、是否满员；关键字搜索。
- 房间名 / MOTD 关键词过滤，违规直接拒绝写入。
- 私密房：设置口令，列表显示锁标记，输入口令才下发邀请码。
- 统计接口：在线房间数、玩家总数、热门版本（可复用到版本页）。

---

## 六、部署

- **配置**：阿里云轻量应用服务器 2 核 2G 足够。大厅只发几百字节 JSON，不转发游戏流量，带宽 1~2 Mbps 即可。
- **备案**：国内节点绑域名走 80/443 需要 ICP 备案。不想备案就选香港/新加坡节点，或直接用 IP + 高位端口。
- **HTTPS**：建议用 Caddy 自动签证书；客户端已同时支持 `http://` 和 `https://`。
- **持久化**：单进程 + 内存存储即可，重启丢房间可以接受——房主的心跳会自动补回来。

---

## 七、风险与注意

1. **陶瓦房间强依赖房主在线**，房主一退房间就失效，所以心跳 + 超时下架是必需品，不是优化项。
2. **公开大厅必然会有垃圾房间**，限流和字段校验要先做好，必要时改成邀请制或白名单。
3. **不要急着做中继**。有人 P2P 打不通时才需要转发游戏流量，那是真正的带宽成本（单人约 50~100 KB/s）；先用陶瓦的公共节点顶。
4. 房间邀请码属于半敏感信息，公开展示前想清楚是否要加口令或登录门槛。

---

## 八、建议的推进顺序

1. 阶段一（服务端）→ 本地起服务，用改 `hall_url` 指向 `127.0.0.1` 联调。
2. 阶段二（上报）→ 打通"开房即上榜"的闭环。
3. 真租服务器后只改部署地址，代码不动。
4. 阶段三按实际用户量再补。

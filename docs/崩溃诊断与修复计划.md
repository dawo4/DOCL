# 崩溃诊断与一键修复 · 实施计划

目标：能在启动前发现的问题不留给崩溃；崩了之后能给出准确原因，并且「一键修复」真的能修好，而不是只给建议。

## 二、阶段一：启动前自检（Preflight）

> 状态：**已实现**（`src-tauri/src/preflight.rs`）。当前覆盖版本清单、客户端 jar、启动库、重复 Mod、磁盘空间、路径长度、内存分配、32 位 Java。

在点击启动、真正拉起 Java 之前跑一遍检查，问题当场给出修复入口。

**检查项**

- Java 版本是否满足该实例要求（`expected_java` 已有映射）。
- 分配内存是否超过物理内存的合理比例；是否在用 32 位 Java。
- 版本清单里的库、启动 jar 是否缺失或为 0 字节（复用 `needs_rebuild`）。
- 同一个 modid 是否装了多份；同名不同版本的 jar。
- 游戏所在磁盘剩余空间（建议阈值 2 GB，整合包更高）。
- 游戏目录路径长度、是否含特殊字符。

**分级**

- **阻断**：Java 版本不符、库文件缺失且无法补、内存参数非法 → 不允许启动，直接给「修复」。
- **警告**：磁盘空间紧张、路径过长、重复 Mod → 允许继续，但要显式提示。

**验收**：人为构造 5 种上述问题，启动前都能被拦截或提示，且不会进入启动流程。

## 三、阶段二：远端规则库

> 状态：**已实现**。规则文件为仓库根目录的 `crash-rules.json`，客户端经 jsDelivr 拉取并缓存到数据目录。
> 支持 `"match": "any"`（默认，任一 pattern 命中）与 `"match": "all"`（全部 pattern 同时命中）两种模式。

把 `RULES` 从编译期常量改成「内置兜底 + 远端覆盖」。

- 远端文件 `rules.json`，字段与现有 `Rule` 对齐：`id / title / summary / patterns / advice / links / priority / category`，另加 `rules_version`。
- 每次启动先读本地缓存作为兜底，再在后台拉取最新规则覆盖；拉取失败或校验失败时保留缓存与内置规则，保证离线可用。
- 规则只做纯文本匹配，不包含任何可执行内容；限制单条 `patterns` 数量与长度，防止远端配置异常拖慢分析。
- 规则命中时记录规则 id，为后续统计做准备。

**验收**：只改远端 `rules.json`、不发新版客户端，即可让已经安装的版本识别新的报错。

## 四、阶段三：补齐高频报错

> 状态：**已完成**。`crash-rules.json` 现有 24 条远端规则，覆盖下面清单里的 21 项；
> 引擎侧的四个改动（分级短路、读取 `debug.log`、堆栈关键字反查、退出码闸门）也已落地。
> 主动跳过：Fabric 自带解决方案（需要展示原文，当前规则模型做不到）、client/server-only 混装（pattern 太宽易误报）。

参考 PCL2 的 `ModCrash.vb`（46 类原因）整理出的差距清单，按价值排序。

**A. 环境与 Java**

1. **磁盘空间不足**：`no space left on device`、`not enough space on the disk`。
2. **路径过长 / 非法字符**：`filename or extension is too long`、`invalidpathexception`、`malformed input`。
3. **VC++ 运行库缺失**：`0xc000007b`、`api-ms-win-crt-`。
4. **32 位 Java 明确诊断**：`invalid maximum heap size`、`could not reserve enough space for 1048576kb object heap`（现在会笼统归到内存不足 / 参数错误）。
5. **Java 位数不匹配**：`can't load this .dll on a amd 64-bit platform`。
6. **Java 版本过高**：`nosuchfieldexception: ucp`、`because module java.base does not export`、Nashorn / LambdaMetafactory 的 `classnotfoundexception`。
7. **使用 JDK / OpenJ9**：`classcastexception: java.base/jdk`、`.j9vminternals.`、`open j9 is not supported`。
8. **Mod 需要 Java 11**：`class file version 55.0`、`requested compatibility level java_11 could not be set`。

**B. 显卡与渲染**

9. **驱动导致的 EXCEPTION_ACCESS_VIOLATION**：从 hs_err 的 `# C  [ig` / `atio` / `nvoglv` 判断 Intel / AMD / NVIDIA，直接点名驱动。
10. **光影或资源包导致 OpenGL 1282**：`1282: invalid operation`。
11. **材质过大**：`maybe try a lower resolution resourcepack?`。
12. **OptiFine 与 Sodium / Embeddium 并存**：专门提示「只能保留一个」，而不是笼统归到 Mixin。
13. **OptiFine 与 Forge 不兼容**：一组固定 `NoSuchMethodError` 签名（`SpriteContents.<init>`、`RenderSystem.getBackendDescription`、`BakedQuad.<init>` 等）。
14. **ShadersMod 与 OptiFine 同时安装**。

**C. Mod 安装问题**

15. **Mod 文件被解压**：`extracted mod jars found`、`directories below appear to be extracted jar files`。
16. **MixinBootstrap 缺失**：`classnotfoundexception: org.spongepowered.asm.launch.mixintweaker`。
17. **Mod 名含特殊字符**：`invalid module name: '' is not a java identifier`。
18. **Mod 过多超出 ID 限制**：`maximum id range exceeded`。
19. **Mod 配置文件损坏**：`failed loading config file ... of type`。
20. **文件签名校验失败**：`signer information does not match`。
21. **客户端 / 服务端专属 Mod 混装**：`client-only`、`server-only`、`attempted to load`。

**D. 加载器**

22. **Forge 安装不完整**：`cannot find launch target fmlclient`、`invalid paths argument ... fmlcore`。
23. **版本 JSON 中存在多个 Forge**：`found multiple arguments for option fml.forgeversion`。
24. **NightConfig 的 Bug**：`parsingexception: not enough data available`。
25. **Fabric 自带解决方案**：`a potential solution has been determined:` 后面列出的条目直接读出来展示。
26. **Fabric API 缺失**：`requires any version of fabric-api`，附直接下载入口。

**E. 世界与其它**

27. **特定方块 / 实体**：从崩溃报告提取 `Block location` / `Entity Type`，比「存档损坏」精确。
28. **玩家手动触发调试崩溃**：`manually triggered debug crash`，用于排除误报。
29. **极短的程序输出**：日志不足 100 字符且没有正常启动痕迹。
30. **启动器自身问题**：WebView2 缺失、数据目录只读、更新失败——目前完全没有覆盖。

**匹配机制改进**

- **分级短路**：像 PCL 一样分三级（高优先精确匹配 → Mixin/加载器专项 → 低优先兜底），某一级命中就停止，避免次要规则干扰主因。
- **补充日志源**：增加 `logs/debug.log`（`latest.log` 会被截断，`debug.log` 更完整）。
- **堆栈反查 Mod 增强**：支持 Mixin 的 `xxx$yyy$zzz` 形式堆栈，以及 Fabric 崩溃报告里的 Mod 列表格式。
- **退出码闸门**：退出码为 0 时，不把日志里的普通异常判成崩溃；退出码非 0 但没命中规则时仍走通用兜底。
- **native 崩溃特征**：`looks_like_crash` 增加 hs_err / access violation 等特征，减少漏报。

## 五、阶段四：修复能力增强

> 状态：**已完成**。备份与一键回滚、修复后自检、Mod jar 完整性校验、缺失前置自动安装、
> Java 自动切换、图形设置重置、assets 补全均已落地。
> 其中补前置、画质重置、补资源文件三项在「一键修复」入口里由用户显式勾选，默认关闭。

| 项目 | 说明 |
| --- | --- |
| 缺失前置自动安装 | 复用 `moddeps` 解析依赖，从 Modrinth / CurseForge 补装 |
| jar 完整性校验 | Zip 打开测试，损坏的直接重新下载 |
| assets 补全 | 校验资源索引与对象文件 |
| Java 自动切换 | 按命中规则直接切到合适的 Java，而不是只提示 |
| 图形设置重置 | 一键把渲染距离 / 光影恢复默认，解决 OOM 与 OpenGL 问题 |
| **备份与回滚** | 修复前把要改的文件（版本 json、被禁用的 Mod）打包备份，支持一键还原 |
| 修复后自检 | 修完再跑一次 Preflight，输出「已修好 / 仍需手动处理」清单 |

**原则**：所有写操作都要先备份；修复报告要写清「动了哪些文件」，不能只说一句「修复完成」。

## 六、阶段五：匿名统计（可选，默认关闭）

- 用户明确同意后才上传，内容仅限：规则 id、Java 版本、加载器、游戏版本、Mod 数量、修复是否成功。
- 不上传日志正文、路径、账号信息。
- 用途：统计规则命中率、误报率、修复成功率，指导下一轮规则调整。

---

## 七、风险

1. **误报比漏报更伤用户信任**：规则尽量带上下文条件（退出码、日志时间段），宁可提示得保守一些。
2. **远端规则不可用**：必须有完整的内置兜底，网络异常不影响崩溃分析。
3. **自动修复会改用户文件**：备份 + 回滚是硬性要求，尤其是禁用 Mod 这类操作。
4. **隐私**：任何上传都必须显式同意，默认关闭。

---

## 八、推进顺序

1. 启动前自检（收益最大，且不依赖崩溃样本）。
2. 远端规则库（决定后续迭代速度）。
3. 补高频规则（磁盘、路径、运行库、位数、OptiFine 冲突等）。
4. 修复能力增强（自动装前置、校验 jar、备份回滚）。
5. 匿名统计（有数据之后再做）。

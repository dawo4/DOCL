# 启动器导入计划

> 目标：把用户已有的游戏实例从其他启动器接管过来，只读原目录、不复制、不改原文件。
> 已完成 PCL 与 HMCL；其余启动器按本文顺序排期，未实施前不影响现有功能。

## 一、已完成

### 1. PCL2 / PCL2 社区版

- 识别：`.minecraft`、`PCL.ini`、注册表 `HKCU\Software\PCL`、`versions/<id>/PCL/Setup.ini`。
- 读取：全部游戏文件夹（`LaunchFolders` / `LaunchFolderSelect`）、内存、Java、窗口、更新策略、下载源。
- 隔离：优先用 PCL 版本级 `VersionArgumentIndieV2`，缺失时按 mods/资源包/光影/存档的实际位置推断。
- 附加：清理清单里同一 Maven 坐标的重复依赖（保留 `.pcl-import.bak`）。

### 2. HMCL

- 识别三种布局：
  - **3.16+**：`.hmcl/config/game-directories.json`、`launcher-settings.json`、`game-settings.json`；
  - **3.x**：启动器目录下的 `hmcl.json`（旧版 `.hmcl.json`），用 `configurations` 保存多套启动配置；
  - **更早版本**：`hmcl.json` 的扁平字段 `gameDir`、`selectedProfile`、`maxMemory`、`javaDir`、`javaArgs`。
- 3.16+ 读取：`directories[]` 的游戏目录与显示名、`selectedGameDirectory`（当前目录）、
  `selectedInstance`（每个目录上次启动的版本）、预设里的内存/窗口/JVM 参数/游戏参数/启动前命令、
  `fileDownloadSource` 下载源、`defaultIsolationType`（NEVER / ALWAYS / MODDED）。
- 3.x 读取：`configurations` 里的多套配置，各自有 `gameDir`、`useRelativePath`、
  `selectedMinecraftVersion`，`last` 指向当前配置。
- 隔离：优先按 `mods / 资源包 / 光影 / 存档` 的实际位置判断；判断不出来时按 HMCL 的隔离策略推断
  （MODDED 只隔离加载器/整合包版本）。
- 也允许直接选 `.minecraft` 或其外层目录，此时只接管目录。

## 二、待实施

### 1. MultiMC / Prism Launcher（优先级：高）

- 识别：`instances/<实例>/instance.cfg`（INI）+ `mmc-pack.json`（组件版本）+ `.minecraft/`。
- 读取：
  - `instance.cfg`：`name`、`JavaPath`、`MaxMemAlloc`、`OverrideMemory`、`OverrideJavaArgs`、`JvmArgs`、`MinecraftArgs`；
  - `mmc-pack.json`：`net.minecraft`、`net.fabricmc.fabric-loader`、`net.minecraftforge`、
    `org.quiltmc.quilt-loader`、`net.neoforged`，用于生成实例的加载器/版本说明。
- 落地：每个实例目录就是一个独立游戏目录，登记进「游戏目录列表」，隔离恒为「开」。
- 注意：Prism 与 MultiMC 格式相同，一个解析器通吃；实例目录名可能含空格与中文。

### 2. CurseForge（优先级：中）

- 识别：`%USERPROFILE%\curseforge\minecraft\Instances\<实例>\minecraftinstance.json`。
- 读取：`name`、`gameVersion`、`baseModLoader`（name/version）、`installedMods` 数量。
- 落地：实例目录直接接管；如果只有导出的整合包 `.zip`，走现有整合包导入流程。
- 注意：只导入本地已安装实例，不触发 CurseForge 的重新下载。

### 3. ATLauncher（优先级：中）

- 识别：`%APPDATA%\ATLauncher\instances\<实例>\instance.json`。
- 读取：实例名、游戏版本、加载器（Forge/Fabric/Quilt/NeoForge）与版本。
- 落地：实例目录接管；隔离开启。

### 4. GDLauncher（优先级：低）

- 识别：`%APPDATA%\gdlauncher_next\instances\<实例>\instance.json`（旧版为 `gdlauncher`）。
- 读取：实例名、游戏版本、加载器版本。
- 落地：实例目录接管；隔离开启。

### 5. Modrinth App / Axolotl（优先级：低）

- 识别：`%APPDATA%\com.modrinth.theseus\profiles\<id>\profile.json` + `app.db`（SQLite）。
- 读取：实例名、加载器、游戏版本；内容目录在 profile 文件夹内。
- 落地：profile 目录接管，隔离开启。
- 注意：要读 SQLite，依赖与兼容成本最高，放在最后。

## 三、公共设计

1. **只读原目录**：不移动、不复制、不改原启动器配置；需要备份时只备份即将修改的 DOCL 侧元数据。
2. **接管而非迁移**：把目录登记进「游戏目录列表」，实例元数据写入显示名、隔离、内存、Java。
3. **预览后再落盘**：先返回检测结果（目录、配置名、版本数、隔离推断），用户确认后再写入。
4. **隔离判定复用** `launcher_layout`：
   - 有显式记录（如 PCL）优先用记录；
   - 没有记录时按 `mods / resourcepacks / shaderpacks / saves / config` 的实际位置推断；
   - 两边都有内容或都为空时不覆盖用户当前设置。
5. **账号不迁移**：各启动器的令牌都是加密存储，统一提示重新登录。
6. **失败可解释**：路径不存在、配置文件损坏、没有 `versions` 目录时给出明确原因，不静默跳过。

## 四、测试要点

- 多目录：同一启动器配置多个游戏文件夹时全部登记，当前项设为活动目录。
- 路径归一：外层目录包含 `.minecraft` 时自动换算到内层。
- 隔离：根目录有 mods、版本目录为空 → 非隔离；版本目录有 mods → 隔离。
- 重复导入：同一目录导入两次不产生重复条目，已有实例设置不被覆盖。
- 缺配置：只选 `.minecraft` 时仍能接管，并提示「只导入了目录」。

## 五、暂不做

- 复制模式（整包拷入 DOCL 目录）：占用翻倍，且与「接管」语义冲突，除非用户明确要求。
- 导入时自动补下载缺失的运行库：DOCL 是传统目录结构，原启动器装好的文件可直接复用。

## 六、整合包更新（已实现）

版本页「快捷方式」里新增「更新整合包」：选择一个新版整合包文件，先比对再更新。

- 支持格式：
  - Modrinth 格式（`.mrpack`，也兼容 DOCL 自己导出的包），清单自带路径与直链，直接解析；
  - CurseForge 整合包（`manifest.json`），联网把 `projectID/fileID` 解析成文件名、直链与 SHA-1 后映射到 `mods/<文件名>`；
  - 通用 ZIP 没有文件清单，拒绝更新并提示改用整合包原始文件。
- 比对依据：
  - 新版清单里的每个文件按 SHA-1 与磁盘现状比较，缺文件算「新增」，内容不同算「更新」；
  - 旧清单依次取 `.docl-pack.json`、`modrinth.index.json`、HMCL 的 `modpack.cfg`，
    旧清单里有、新清单里没有且磁盘上仍存在的文件算「移除」；
  - 没有旧清单时只增改、不删除，并在预览里提示。
- 更新动作：备份会被覆盖/删除的文件与 overrides → 下载变更 → 解压覆盖目录（CurseForge 按 manifest 的 `overrides` 字段）
  → 删除已移除文件 → 写入 `.docl-pack.json` 供下次比对。
- 导入时也会写入 `.docl-pack.json`（CurseForge 与 Modrinth 两个分支），导入后即可继续用新版整合包更新。
- 保留用户内容：只处理清单内文件，额外添加的 Mod、存档、截图都不动。
- 限制：CurseForge 需要能访问 API（国内建议开启系统代理），个别文件取不到直链时跳过并在预览里列出；
  游戏版本或加载器变化时只提示，不自动切换；未启用版本隔离的实例会拒绝更新。

## 七、导出整合包

- 通用 ZIP：`{名称}/manifest.docl.json` + `{名称}/.minecraft/…`，兼容各启动器。
- Modrinth `.mrpack`：`modrinth.index.json` 带完整 `files[]`——导出时把 `mods/`、`resourcepacks/`、
  `shaderpacks/`、`datapacks/` 顶层的文件按 SHA-1 批量反查 Modrinth，命中的写入 `path/downloads/hashes/fileSize`
  （能取到项目信息时附带 `env`），其余文件（自改 Mod、配置、存档等）放进 `overrides/`。
  这样别人用 Modrinth 生态打开时能识别出对应项目版本，并继续按 Modrinth 更新。
- 反查失败（离线、接口异常）时自动降级：所有文件照旧放入 `overrides/`，导出不中断。
